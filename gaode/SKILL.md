# 周边去哪儿：步行可达地点推荐

单轮任务：给定起点坐标和一句自然语言需求，返回最多 3 个从**同一起点**步行可达的地点，每个地点给出名称、地址、步行距离、步行时间与一句有数据依据的推荐理由。

## 1. 适用边界

- 输入通常包含城市、起点坐标（高德格式为「经度,纬度」，**经度在前，禁止颠倒**）和自然语言需求；起点由任务提供，不做设备定位。
- 各地点都是同一起点的独立备选：**不要串成多站行程**（不要把 A 写成去 B 的途经点、不要规划游玩顺序）；列表按第 4 节的步行时间排序，这只是「备选排序」，不是行程顺序。
- 不做驾车/公交/骑行方案，不查天气，不做多轮追问。
- 评测为单轮：缺参数用第 2 节默认值，并在回答首行写明假设，**不要反问显而易见的信息**。

## 2. 解析需求（一次性完成）

| 字段 | 说明 | 缺失时 |
|---|---|---|
| 城市 | 用于同义词与地名消歧 | 不猜，直接用起点周边搜索 |
| 起点坐标 | 「经度,纬度」原样使用 | 只有地名时才用地理编码工具换算，并说明起点据此确定 |
| 地点类型/关键词 | 咖啡馆、餐厅、公园、便利店等 | 无法判断时按通用「附近好去处」处理并说明 |
| 多类型需求 | 如「咖啡馆或餐厅」「公园或绿地」 | 每个类型各搜一次再合并去重，总候选仍受第 4 节上限约束 |
| 步行时间上限 | 单位分钟，如「15 分钟内」 | 不设硬上限，按步行时间由近到远排序 |
| 推荐数量 | 用户要几个 | 默认 3，且**最多 3 个** |
| 偏好 | 优先近、安静、便宜等 | 无偏好时按步行时间升序 |

写进回答的假设与换算：

- `time_limit_sec = 分钟 × 60`（下文的「上限」都指这个秒数）
- `search_radius_m = clamp(分钟 × 100, 300, 50000)`；无时间上限时用 1500。
  依据：步行约 80 米/分钟，再留约 25% 余量；搜索半径只决定召回范围，**是否达标只由步行路线时长决定**。
- 坐标按高德格式（经度,纬度）理解并原样传给工具，**不要自行做坐标系换算**；坐标明显异常（如纬度超出 -90~90、经纬度写反）时按参数错误处理。
- 关键词同义词（搜索为空时各换一次）：咖啡馆→咖啡/咖啡厅；餐厅→美食/餐厅；公园→公园/绿地；便利店→便利店/便民商店；药店→药店/大药房；厕所→公共厕所。

## 3. 可用工具（以平台实际暴露的工具名为准）

| 能力 | 常见工具名 | 关键参数 | 用途 |
|---|---|---|---|
| 地点搜索 | `maps_around_search` | `location`、`keywords`、`radius` | 搜索起点周边候选 POI |
| 地点详情 | `maps_search_detail` | `id` | **补 POI 坐标**、取地址等字段 |
| 步行路线 | `maps_direction_walking` | `origin`、`destination` | 取步行 `distance`（米）与 `duration`（秒） |
| 地理编码 | `maps_geo` | `address`、`city` | 仅当任务只给地名时换算起点 |

工具名不同时按参数语义匹配，不要因为名字不一致就放弃查询。

- **坐标必须来自工具返回**：周边搜索结果通常只返回 `id / name / address / typecode`，**不含坐标**；此时必须用详情工具按 `id` 取 `location`。搜索结果自带坐标则直接使用。
  若平台没有暴露详情工具，可用地理编码工具以「名称 + 城市」补坐标；仍然取不到坐标的地点一律剔除，**禁止估算、禁止用地图记忆补坐标**。
- 搜索无结果的正常形态是 `{"pois":[]}`（不是报错）；工具报错的形态包含 `API 调用失败：<原因>`、连接中断或超时。
- `distance`、`duration` 可能是数字也可能是字符串，比较前统一转成数字，**不要按字符串比较**。

## 4. 固定执行流程

1. **搜索**：周边搜索，`location`=起点，`keywords`=主关键词，`radius`=第 2 节换算值。
2. **判空**：结果为空则换一个同义词或把半径放大到 1.5 倍各试一次（半径 ≤ 50000），并在回答中说明实际使用的关键词与半径。
3. **取坐标**：取搜索结果的前 10 个候选（结果不足 10 个则全取；返回顺序通常由近到远，但没有距离字段时不能保证），缺坐标的用详情工具补。
4. **查路线**：对每个有坐标的候选调用步行路线，`origin`=起点，`destination`=候选坐标；取 `paths[0]` 的 `distance` 与 `duration`，返回多条时也以第一条为准，**不要为了显得近而挑最短的一条**。
5. **硬过滤**：类型匹配 → `duration ≤ 上限`（用原始秒数比较，**先比较后取整**）→ 同质去重 → 截断到 `min(用户数量, 3)`。
   若达标数量少于目标且候选已全部检查完，可把半径放大 1.5 倍补搜一次（≤50000），对新增候选重复第 3–5 步，并在回答中说明补搜；补搜只增加召回，**不降低时间上限**。
6. **排序**：用户说「优先近」或未表态时，都按 `duration` 升序，相同再按 `distance` 升序、再按名称；在回答里说明排序依据。
7. **输出**：按第 6 节格式作答。

调用纪律：

- 路线查询只对候选池执行，**串行调用、不要并发批量请求**；高德接口有 QPS 限制，并发容易触发 `CUQPS_HAS_EXCEEDED_THE_LIMIT`。
- 单次工具调用失败（含 `API 调用失败：…`、连接中断、超时）**间隔片刻（约 1 秒）后重试 1 次**；仍失败就按第 7 节如实说明该候选或该能力不可用，不得编造。

## 5. 筛选规则

- **类型匹配**：名称或**主类型**（`type` 的第二个分号段，如「咖啡厅」「公园广场」「便民商店/便利店」）体现关键词或同义词才算匹配；没有 `type` 字段时用 `typecode` 或名称判断。仅次要类型命中不算，例如搜「便利店」时，主类型为「超级市场」的超市即使带便利店副标签，也不能当作便利店推荐。
- **时间过滤**：`duration`（秒）≤ 上限秒数。不满足的候选**不得**出现在推荐列表里，包括「接近上限」的（例如上限 900 秒时，902 秒也必须排除）。
- **同质去重**：同一地点的不同入口/子点位只保留一个——名称一方是另一方的末段（如「中心公园」与「滨河景区-中心公园」），或两个 POI 坐标相距 ≤150 米且名称相同/互相包含。保留步行时间更短的一条，并在说明中写明合并了几个重复点位。
- **数量**：最多 3 个；用户要求更少时按用户要求，要求更多时也只给 3 个并说明上限。
- **排序稳定性**：并列时按距离、名称兜底，保证每次输出顺序一致。

## 6. 输出格式

首行给起点与筛选条件（含假设），随后用有序列表，每项三行以内：

```
起点：<起点描述>（<经度>,<纬度>）｜筛选：<类型> · 步行 ≤<上限> 分钟 · 最多 <数量> 个[ · 优先近]

1. **<地点名称>** — <地址>
   步行 **<X> 米** / 约 **<Y> 分钟**
   理由：<一句引用工具数据的话>

以上地点均从同一起点出发，为独立备选。
```

- 距离、时间必须来自步行路线工具：米数照抄，分钟由秒数**向上取整**换算并用「约」（如 294 秒写「约 5 分钟」）；筛选比较用原始秒数，回答中不必逐条展示秒数，**不得改写原始值或把超时写达标**。
- 任务没给起点地名时，首行只写一次坐标，例如「起点：（经度,纬度）｜筛选：…」，不要重复写两遍。
- 推荐理由只复述工具字段（步行秒数、米数、类型、地址特征）或据此做比较，例如「本次候选中步行时间最短」「比第 1 家多 41 秒」。禁止「环境安静」「人少」「新店」这类没有工具依据的评价。
- 结果不足、淘汰与异常说明放在列表之后、「以上地点…」之前。
- 某个字段缺失或无法核实时，按第 8 节写「地址未提供」「未核实」，不要用推测填满格式。

## 7. 异常与结果不足（必须如实说明）

| 情况 | 处理 |
|---|---|
| 搜索为空 `{"pois":[]}` | 换同义词、扩半径各 1 次；仍为空则说明已试关键词与半径，建议放宽时间或换类型，可以给 0 个推荐 |
| `API 调用失败：INVALID_PARAMS` | 多为坐标/参数格式错误：核对「经度,纬度」顺序与取值，修正后重试 1 次 |
| `API 调用失败：OUT_OF_SERVICE`、`ENGINE_RESPONSE_DATA_ERROR`、连接中断 | 服务或网络异常：间隔片刻后重试 1 次，仍失败则说明「高德 XX 服务暂时不可用」，不输出未查到路线的地点 |
| `API 调用失败：CUQPS_HAS_EXCEEDED_THE_LIMIT` | 限流：减少本次候选数、间隔片刻后重试 1 次；仍失败则剔除受影响候选并计数，已成功的结果照常输出 |
| 详情无坐标 / 路线无数据 / 路线失败 | 剔除该候选并计数，**不得**用直线距离、驾车距离或估算值替代 |
| 部分候选超时 | 只输出达标的；说明「共检查 N 个候选，M 个超出步行上限或无法获取路线」 |
| 全部候选超时 | 给 0 个推荐，列出最近候选的**实际步行时长**并说明超出上限多少，建议把上限放宽到至少「实际秒数向上取整的分钟数」（放宽后需重新查询才能确认） |
| 达标数量少于要求 | 按实际数量输出，说明「仅找到 N 个符合条件的地点」及被类型/时间/重复/路线淘汰的数量 |

## 8. 数据纪律

- 名称、地址、距离、时间**只能来自工具返回**；地址为空或 `[]` 时写「地址未提供」，地址字段是别的 POI 名称时也照原样引用，不要「修正」。
- 不编造评分、营业状态、排队情况、安静程度、人气、优惠；没有工具字段依据的一律写「未核实」。
  例外：详情工具明确返回 `rating`、`open_time` 等字段时可原样引用并注明来自高德详情，其余仍写「未核实」。
- 不使用直线距离、`maps_distance` 结果或记忆中的地点替代步行路线。
- 回答中的每个数字都要能在本次工具调用记录里找到出处；回答不要提密钥、内部字段名或工具调用流水账，只给结论与依据。

## 9. 收尾自检（逐条确认后再作答）

1. 每个地点都有工具返回的名称、`distance`、`duration`，地址是工具返回值或已标注「地址未提供」，且用原始秒数验证过 `duration ≤` 上限？
2. 超时、无坐标、路线失败的地点是否已全部剔除，而不是降级展示或四舍五入后保留？
3. 是否做了同质去重，且数量 ≤ `min(用户要求, 3)`；不足时说明了原因与淘汰数量？
4. 有没有编造信息、把「未核实」写成事实、或把独立备选写成行程？
5. 失败的调用是否按要求重试过一次，并在回答中如实说明？
